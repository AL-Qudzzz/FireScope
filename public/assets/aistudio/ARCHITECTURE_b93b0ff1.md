# Architecture

## Goals
Deliver the calendar quickly; preserve raw observations; separate sensor ingestion from harmonized aggregates; support global scale without sending all raw points to the browser.

## Logical flow
```text
NASA FIRMS / challenge resources
          |
   Data acquisition
          |
 Immutable raw files + checksums
          |
 Parsing + schema validation
          |
 Canonical observations
          |
 Sensor-specific QA + provenance
          |
 Spatial/temporal aggregation
          |
 Comparative or validated harmonized metrics
          |
 DuckDB + Parquet
          |
 FastAPI
          |
 React + MapLibre + ECharts
```

`data/raw` and `data/processed` should be git-ignored. Commit only small documented fixtures.

## Provisional stack
- Frontend: React + TypeScript + Vite.
- Map: MapLibre GL JS.
- Charts: Apache ECharts (calendar heatmap and time series).
- Backend: Python + FastAPI + Pydantic.
- Processing: Pandas, NumPy, SciPy; GeoPandas/Shapely only as needed.
- Storage: DuckDB + Parquet.
- Add PostGIS only if persistent multi-user spatial querying requires it.

## Data layers
- Raw: exact downloaded source files, immutable, checksummed.
- Canonical: normalized field names/units while retaining source fields and native semantics.
- Aggregated: sensor/platform-specific counts and summaries by AOI/grid/time bin.
- Harmonized: only metrics generated by a documented and validated method.

## Performance
Aggregate on backend; query by AOI/time; cluster or grid-aggregate map data; paginate raw observations; cache repeated queries; bound payloads.

## Reliability
If live NASA access fails, use a small documented NASA sample snapshot if permitted. Show retrieval timestamp and source status. Never silently fall back to fabricated data.
